# Feature status

Shelf is honest about its own maturity, not only about its data. Every feature
declares a real state in a register (`shared/src/feature-status.ts`), served at
`GET /api/v1/meta/features` and shown in the admin console. Nobody —
operator, reviewer or user — has to reverse-engineer from the UI whether
something is wired to a live source.

The states:

- **PRODUCTION_READY** — implemented end to end against live provider data.
- **PARTIAL** — implemented, but a dependency limits it (a capability, a
  credential, a scope).
- **INTEGRATION_PENDING** — the code exists and is exercised by tests, but there
  is no live integration yet.
- **PLANNED** — designed and typed, not implemented.

`PARTIAL` and `PLANNED` are legitimate states to ship in. Presenting either as
`PRODUCTION_READY` is not. This document is the register in prose; the register
itself is the source of truth.

## Production-ready

- **Search — NL parsing, parallel aggregation, streaming progress, ranking.**
  Hebrew/English extraction with removable tokens; concurrent per-provider
  querying with timeout, rate limit and circuit breaker, degrading to the
  sources that answer; real per-provider SSE state (no synthetic percentage);
  hard-filter-then-score ranking with no commission input.
- **Matching — identifier-based and heuristic.** Checksum-validated GTIN and MPN
  agreement produce `EXACT_MATCH`; variant conflicts demote and are excluded
  from single-product price rows; heuristic similarity is capped below identity.
- **Pricing — total-cost model.** Item/shipping/tax/discount/coupon combine with
  state propagation; any estimated or missing component prevents an exact total.
- **Coupons — verification states.** Six-state model; only `VERIFIED` codes are
  deducted; no code is ever generated by us.
- **Deals — radar.** User subscriptions are refused at creation when the chosen
  providers cannot support deal discovery, with the reason returned.
- **Affiliate — click tracking.** Clicks recorded against a rotating session
  hash, separate from personal data, with placement and country.
- **Compliance — policy registry, capability gates, kill switches.** Versioned,
  DB-backed, operator-editable, audited; every provider read is capability-gated;
  kill switches are effective immediately without a deploy.
- **Accounts — RBAC and privacy controls.** Server-enforced guest limits (tested
  by calling endpoints directly); history off by default; export and deletion.
- **Cart — smart cross-store cart.** Per-store shipping and totals; explicitly
  not a checkout.
- **Admin — compliance center, source health, product debugger.**
- **Analytics — event pipeline.** Allowlisted properties; session-scoped by
  default.
- **Platform — demo fixtures, caching.** Fixtures tagged and blocked in
  production; cache TTL capped by each provider's policy and re-dated.

## Partial

- **Pricing — tax estimation.** Destination VAT yields a labelled estimated
  range; import duty, de-minimis and carrier fees are reported as not computable
  rather than estimated. *Needs a duty/landed-cost source per country.*
- **Pricing — currency conversion.** Dated-rate conversion with the rate's
  as-of date on every figure; the static table ships for dev. *Needs
  `FX_DRIVER=http` with a real feed.*
- **Pricing — price history.** Observation store, series and percentiles,
  gated on `priceHistory` + `persistProviderData`. *Needs per-programme
  confirmation that retaining observations is permitted.*
- **Deals — hunter.** Seven evidence kinds; the history-based ones are genuinely
  thinner where observation retention is not permitted.
- **Affiliate — link engine.** Per-adapter construction, host allowlist,
  forbidden-parameter checks, disclosure resolution; falls back to the plain
  store URL when unconfigured. *Needs programme credentials per provider.*
- **Compliance — provider terms verification.** Defaults are conservative; many
  ship `VERIFICATION_REQUIRED`. *Confirming them against each programme is a
  release gate, not a code task — see [compliance.md](compliance.md#the-release-gate).*
- **Accounts — Google OAuth.** Full PKCE flow, rotating sessions,
  server-side revocation. *Needs `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`.*
- **Alerts — engine.** Capability-gated creation per kind/provider; in-app
  delivery is immediate. *Needs SMTP for e-mail; `MAIL_DRIVER=console`
  otherwise.*
- **Platform — queue.** Driver abstraction with in-memory (single-process) and
  Redis implementations. *Needs `QUEUE_DRIVER=redis` for multi-instance.*

## Integration pending

- **Coupons — provider ingestion.** Adapter interface, store, checker worker and
  eligibility model are complete; live ingestion runs only for providers whose
  `coupons` capability is `AVAILABLE` and configured. *Needs authorized coupon
  endpoints per programme.*

## Planned

- **Search — image lookup.** API contract, capability gate and low-confidence
  copy are defined; no vision model is wired, and the endpoint returns
  `ERROR_CAPABILITY_UNAVAILABLE` rather than a guess. *Needs an image-embedding
  service and a provider-permitted image-search path.*
- **Matching — image similarity.** Signal and weight cap defined; not computed;
  would remain incapable of asserting identity by design.
- **Affiliate — conversion import.** Schema and reporting states exist; nothing
  imports programme reports, and the admin UI shows commission as estimated
  until it does. *Needs programme reporting API access per provider.*
